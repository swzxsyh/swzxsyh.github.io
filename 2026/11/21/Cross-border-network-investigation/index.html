Cloudflare + AWS NLB + Nginx 偶发 520 / 522 / 525 / 499 排查记录(进行中)

发表于 2026-11-21
  • Argo
  • Nginx keepalive
  • Linux TCP bbr

1. 背景与架构

  • 背景：服务从阿里云迁移至 AWS us-east-2（俄亥俄） 后，部分客户端（主要位于新加坡 SG）访问域名时偶发报错。
  • 访问链路：
    客户端 -> Cloudflare -> AWS NLB（单可用区） -> EC2 (Nginx) -> 后端应用 (<app_port>)
  • 源站证书：使用 Cloudflare 签发的 15 年 Origin CA 证书，配置在 Nginx 上。
  • 异常状态码：Cloudflare 日志中出现 525、522、520、524、499，且 originResponseStatus 均为 0。

2. 排查过程

第一阶段：调整代理超时并开启耗时日志（排除应用层卡死）

最初怀疑后端 Java 接口超时导致异常（CF 免费版回源等待上限为 100s，Nginx 默认等待后端超时为 60s），因此将 Nginx proxy_read_timeout 设为 80s，并新增 api_timing 日志监控接口耗时：

排查结果：

  • 对比 CF 报错时间点前后 api_timing.log：所有请求均返回 status=200 upstream_status=200，connect_time=0.000，P95 耗时 0.333s（最大仅 2.685s）。
  • 且因 proxy_read_timeout 为 80s，若后端卡死应先由 Nginx 报 504，而非等 CF 100s 报 524。基本排除 Java 应用与 Nginx 上游代理问题。

第二阶段：调大长连接超时 + 开启 info 级别错误日志

怀疑默认 keepalive_timeout 65 过小导致与 Cloudflare 回源连接池复用冲突，同时原 error_log 为 error 级别会忽略连接/握手异常，于是调整为：

  • 调整后 520 / 524 消失，但夜间（北京时间 21:00 ~ 02:00）仍偶发 522 与 525，且对应时间点 Java 应用依旧无请求进入记录。

3. 根因总结

状态码 归因分析
522 / 525 主要调用方在新加坡（SG），源站在美国俄亥俄（us-east-2）。北京时间夜间国际公网出口拥堵时，Cloudflare 边缘节点 ↔ AWS us-east-2 跨太平洋回源链路出现间歇性丢包：TCP SYN 丢包触发 522，TLS 握手包丢包触发 525（Nginx 侧表现为 60s 后 while SSL handshaking 超时）。
520 / 524 与默认 keepalive_timeout 65 引起的连接复用竞争及跨洋链路抖动有关，调大至 180 后已消除。
499 客户端在等待响应期间主动断开连接（需检查调用方 HTTP 客户端超时配置）。

4. 优化措施与后续方案

已实施：1. 开启 Cloudflare Argo Smart Routing

在 Cloudflare 开启 Argo Smart Routing，使回源流量走 CF 私有骨干网直达源站，避开拥堵的跨洋公网链路。

已实施：2. 开启 EC2 TCP BBR 拥塞控制

Linux 默认 cubic 在跨洋高延迟丢包场景下恢复较慢，已切换为 fq + bbr 以提升跨洋重传与握手恢复能力：

后续观察与长期方案

  1. 短期观察：观察开启 Argo + BBR 后晚高峰 522 / 525 出现频率；排查完成后将 Nginx error_log 恢复为 error 级别，避免 info 日志占用磁盘。
  2. 长期架构方案：若主要业务调用方长期位于亚太地区，建议将源站迁往距离更近的可用区（如 **AWS ap-southeast-1**）。
